# 050: The auth block wins over an authored header

Status: Accepted

## Decision

When a request declares an `auth:` block and also carries an enabled `Authorization` header — or,
for `apikey`, a header named by the block's own `key` — the block wins. The authored entry is
replaced in place, under the name `renderAuth` chose, and any further enabled entry of that name is
removed, so the wire never carries two. The warning names what was replaced and how to keep it:

```
bearer auth replaced request header "Authorization"; delete the auth block to send the header instead
```

`replaceHeader` in `http/headers.ts` owns the surgery and returns the displaced values so the
caller can name them. gRPC does the same to its metadata map. `noauth`, an absent block, and a
block whose token renders empty all still leave the authored entry exactly as written, because
those render to `none` and never reach this branch.

The window says so before a send. The **Headers** pane carries the banner, not the Auth pane, and
`authOverride` in `renderer/model/auth.ts` computes it from the same block the pane edits.

## Rationale

preman had it backwards, and nothing recorded that as a choice.

The driving case is a real workspace. `Admin > AI > Zalopay kimi` declares
`auth: {type: bearer, credentials: {token: sk-…}}` and, seven lines above it, a header
`Authorization: Bearer $KEY`. `$KEY` is shell syntax; preman has no `$` interpolation, so those
five characters went on the wire literally and the request 401'd. The token sat in the file, in the
Auth tab, correct, and unused. Ten requests in that one workspace declare both.

Postman resolves this the other way, and not by convention — by code. `postman-runtime`'s
`lib/authorizer/bearer.js` signs with `request.removeHeader('Authorization', { ignoreCase: true })`
and then adds its own; `basic.js` is identical; `apikey.js` does the same by the block's own key
name, and `url.query.remove` for the query target. The docs say it in words: "You can't override
headers added by your Authorization selections in the Headers tab. If you need auth headers that
are different from those generated by Postman, change your setup in Authorization." There is no
duplicate header and no precedence to reason about — the authored one is gone before the request
is built.

This repository already claims that alignment for the neighbouring rule. `docs/reference.md` says
authentication is inherited "following Postman v2.1", and the runner warns when it inherits. The
override direction sat four lines above that sentence, documented, unjustified, and opposite. There
is no ADR for it and no `why` comment in `http/auth.ts` — the convention this repository holds for
deliberate deviations from Postman. A rule with a warning attached looks decided; this one had only
been implemented.

The two directions are not symmetric in what they cost when wrong. Under the old rule a stale
header silently defeated a correct token, which is the failure that produced this ADR. Under the
new rule a correct header is defeated by a stale block — which is visible in three places: the
banner on the Headers pane, the warning in the Console, and the Auth tab that now shows the block
in named fields rather than as an empty list. The direction Postman chose is also the direction the
tooling can explain.

Rejected:

- **Keeping the old direction and adding the banner.** The cheapest change, and it would have
  spent the window's clearest surface explaining a behaviour that should not exist. A warning is
  not a substitute for the right answer; it is what you write when the answer is expensive.
- **Sending both entries.** What a naive "don't touch the user's headers" reading suggests, and it
  is a different bug: two `Authorization` headers is undefined behaviour at the far end, and RFC
  9110 does not let them be merged the way a list-valued field can.
- **Erroring on the collision.** Defensible, and wrong for a format that people arrive at by
  migration. An imported collection with a leftover header would stop running rather than run the
  way Postman ran it, which is the one thing preman promises.
- **A `settings` key to choose the direction.** Two behaviours, one of which is wrong, and every
  bug report starting with a question about which was set.
- **Removing disabled entries too, as Postman does.** Postman has no disabled header at the point
  it signs — the list it hands the authorizer is already filtered. A disabled row in preman is a
  note the user is keeping; deleting it because of a block they may remove tomorrow destroys
  something no send would have used anyway.
- **Putting the banner on the Auth pane.** The Auth pane is doing the winning; the pane that lost
  is Headers, and that is where Postman shows it too — as an override indication next to the losing
  entry, and as autogenerated headers in the same list.

## Consequences

**This changes what goes on the wire for existing workspaces.** Any request declaring both an
`auth:` block and a matching header now sends the block. That is the point, and for the driving
workspace it fixes ten requests, but a workspace that had come to depend on the old direction —
say a block kept as documentation beside the header actually in use — changes behaviour on upgrade
with only a warning to say so. There is no migration and no opt-out; the warning and the banner are
the whole notice.

Two tests asserted the old direction and now assert the new one, which is the honest record that
this is a behaviour change and not a bug fix: `test/http.test.ts` and `test/e2e.test.ts` each held
a case whose name said the header won.

Copy-as-cURL stays truthful for free. `api/command.ts` builds its command through
`buildHttpRequest`, which is one of `applyAuth`'s four callers, so the command matches the send
without a second implementation to keep in step. `pm.sendRequest` inherits it the same way.

The gRPC path pays a cost the HTTP path does not. `PropertyList` has no positional write, and
`upsert` replaces the first key match whether or not it is enabled — which would leave an enabled
duplicate below a disabled one on the wire. So gRPC does `remove` then `add`, and the replaced
entry moves to the end of the metadata map and takes any disabled entry of the same name with it.
Metadata is a map and order is not observable, so the first is invisible; the second is a real
deviation from the disabled-rows-survive rule, confined to gRPC, and it stands until `PropertyList`
grows a positional write.

`authOverride` declines to answer two questions rather than guess. An `apikey` block with
`in: query` collides with a query parameter, not a header, and the Params pane has no banner. An
**inherited** `apikey` cannot be named at all, because `CatalogNode.auth` carries the type and never
the credentials (ADR 049), and the header's name _is_ a credential. Both return `null`, so the
window is silent where core would still warn. A conformance test runs the real `applyAuth` over the
same data and asserts the prediction matches whether core warns — which is what will catch it if
these two grow apart.

`dropEmptyValues` keeps its behaviour and loses its reason. It dropped blank-valued headers partly
because a blank `authorization:` beside an `auth:` block used to defeat the token; that collision
no longer exists. It still drops them, now on the narrower ground that a header someone started and
did not fill in is more often a mistake than a deliberate empty value — which is a deviation from
Postman, and now the only reason left for it.
